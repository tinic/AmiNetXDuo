# Alignment and stack

A 68000 or 68010 takes an Address Error, which is a Guru and not a slow path, on
a word or longword access to an odd address. The 68020 and later tolerate it, so
this fails only on the machines least able to report why.

| Rule or hazard | Where | Effect |
|---|---|---|
| `__alignof__(long)` on m68k is 2, not 4 | toolchain | GCC never places a `long` at an odd offset in a struct, `AllocMem` is 8-byte aligned and `AllocVec` returns that minus the size longword, and the 68000 keeps SP even in hardware. No compiler-placed or Exec-allocated object in this tree is ever at an odd address, so an Address Error can only come from a pointer we computed: byte arithmetic over wire data, a carve out of a caller's buffer, or a cast of something a caller handed us. `tools/smoke/alignprobe` reports all of it from a running machine |
| A reply carved out of a caller's buffer steps the base up first | `src/bsdsocket/resolver.c:100` | `buf` is an `APTR` from an application and nothing establishes its alignment, so the carve rounds up and counts the slack against `buflen`, leaving a short buffer as `ERANGE` rather than an overrun. Rounding rather than refusing: the caller did nothing wrong by C's rules |
| An `APTR` that arrives across an LVO and is dereferenced wide is refused when odd | `src/bpf/bpf_channel.c:935` | Ten `bpf_ioctl` commands read or write a `ULONG` or `UWORD` through the caller's buffer. The three `ifreq` commands are exempt because they touch bytes only, including the `sockaddr_in` `SIOCGIFADDR` writes by hand |
| The `msg_control` gates test `& 1`, not `& 3` | `src/bsdsocket/cmsg.c:350`, `:482` | `__alignof__(struct cmsghdr)` is 2, so half of all valid control buffers land 2 mod 4, and a longword load from 2 mod 4 is fine on a 68000. `CMSG_BUFFER()` carries `__attribute__((aligned(4)))` because nothing in the language reaches 4 on this target; `& 3` refused the library's own documented idiom about half the time |
| The IP header is at `nx_packet_data_start + AMI_SANA2_RX_PAD + AMI_ETH_HEADER_SIZE`, which is +16, in both receive modes | `src/sana2/sana2_rx.c:533-535` | `src/net68k/n68k_checksum.c` casts the prepend pointer to `ULONG *` and rounds its end pointer on the strength of that identity. Two `_Static_assert`s pin it; changing `AMI_SANA2_RX_PAD` or the physical header size breaks the checksum path |
| `mtod()` has zero call sites | `include/aminetxduo/mbuf.h:182` | `m_data` moves by arbitrary amounts under `mbuf_adj()`, so the first internal user of the macro is the first real instance of this bug class. Nothing is reachable yet: the `mbuf_*` LVOs are all `bsd_enosys` stubs (`src/bsdsocket/bsdsocket_vectors.c:132-142`) |
| A wide cast over a caller's own C object is clean by contract | `options.c`, `mcast.c`, `in6.c`, `errno.c`, `select.c` | A `setsockopt` value, a by-reference `ti_Data`, an `fd_set` and the application's `errno` through `SBTC_ERRNOPTR` are C objects of the cast type, so they are at least even, which is all a longword load needs |
| A library call does not switch stacks | `port/threadx-amiga/src/tx_amiga_adopt.c:251` | The calling Task's own `tc_SPUpper - tc_SPLower` region is handed to `_tx_thread_create()`, so NetX Duo, and with `tls.library` the whole of nx_secure and the bignum code, run on whatever stack the application had. A Kickstart 3.1 Shell gives a command 4 KB, which is why `fetch` brings its own and `clients/compat/amiga_argv.c` swaps before `argv` is built |
| There is no `$STACK:` cookie in the tree and this toolchain's crt0 exports no `__stack` hook | tree-wide | Every stack is an explicit `NP_StackSize`, `tx_thread_create` size or `StackSwap`, so growing a frame is only caught by re-measuring |
| The stack figures in `-fstack-usage` exclude Exec, DOS and ThreadX switch frames | | They are a floor on our own code, not a total, and the SANA-II driver path makes `DoIO`/`SendIO`/`GetMsg` calls at the bottom of the deepest chains. Application hooks (`SBTC_ERROR_HOOK`, the net-monitor hook) are unbounded by construction |
