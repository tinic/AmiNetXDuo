# Receive and transmit rates, bits per second, the MEDIAN of 3 rounds.
# tools/check-rate.sh --update writes this; raising a number belongs in the
# commit that earned it, with the rig named.
#
# rig: playhouse3, -B ens18 -P playhouse2.local.tinic.net
#
# GAINS DO NOT ADD.  MEASURE THE ACCUMULATED SET, NEVER THE SUM OF PARTS.
# 2026-09-06, 3a71a026 against main, six rounds alternated, the base rebuilt to
# md5 7522050095ef for the fourth time that day:
#
#     tcp-rx   5,553,818 -> 5,769,639   +3.89%   (positions +3.38, +4.27)
#     tcp-tx   2,982,376 -> 3,130,634   +4.97%
#
# The two corroborated changes in that range measured +3.16% and +3.09% ALONE,
# which compound to about 6.4%.  Together they are +3.89%.  That is outside the
# noise -- the worst null control that day was +2.75% -- and ahead in both
# positions, so the TOTAL is real and it is the SUM that is wrong.
#
# Two readings, not exclusive.  Freeing CPU moves the binding constraint, so a
# second win converts less than the first: the calibrated burn showed cycles
# converting about one for one at the OLD operating point, not at every point.
# And a single-sitting figure can be flattered, which that day's +2.75% null
# control makes concrete.
#
# Transmit corroborates cleanly: +4.97% end to end against the sweep skip's
# +5.30% measured alone, and that was the only change of the four that moved
# transmit at all.
#
# So quote the end-to-end number for a day's work and keep the per-change
# figures for what each change did on its own.
#
# WHAT THIS GATE CAN AND CANNOT SETTLE -- THREE NULL CONTROLS, 2026-09-06.
# Each is two IDENTICAL binaries, six rounds alternating which arm ran first,
# the arms' md5s checked equal before a round ran:
#
#     morning, two worktrees            rx +0.22%
#     evening, accidental               rx +2.75%   <- ahead in BOTH positions
#     evening, deliberate               rx -0.29%
#
# TYPICAL IS +-0.3%.  THE +2.75% WAS AN EXCURSION, NOT THE FLOOR, and it was
# ahead in both positions, so position agreement does NOT exclude one.  One in
# three observed.
#
# So a six-round A/B is usually tight and occasionally throws a ~3% false
# signal, and A SINGLE A/B CANNOT BE TRUSTED between about 1 and 3 per cent.
# What settles a result in that band is two sittings, or one sitting with a
# same-sitting null control beside it, or a second instrument entirely -- a
# profile share, an RXPROBE counter, a mechanism count.  Every figure this tree
# kept from that day had one: the sweep skip had a null control at +0.22% and
# `sweeps run 1 skipped 927`; the payload alignment had copy_sum_longwords
# falling 15.1 -> 11.7%.  The one that had only a rate A/B, le_rint's +1.53%,
# is recorded as UNPROVEN rather than as a win.
#
# THE ACCIDENT IS WORTH KNOWING TOO: that +2.75% came from an A/B whose two
# arms were the SAME BINARY -- a -D was passed for an option the branch did not
# declare, so it set an unused CMake variable and the code compiled out.  The
# arm md5s are printed before any round for exactly this reason and were read
# only after twelve emulator boots.  READ THEM FIRST.
#
# RAISED 2026-09-06 again, for the third and fourth receive wins of the day:
# dd818cc7 (the LANCE payload two bytes into the buffer, +3.09%) and 6e0893a2
# (le_rint stops rewriting a descriptor field the chip never touches, +1.53%).
#
#     direction   was          now          sittings on this tree
#     tcp-rx      5,594,537    5,770,903    5,824,081 (6 rounds), 5,770,903 (5)
#     tcp-tx      3,127,508    3,133,475    3,133,475 (6 rounds), 3,147,209 (5)
#
# The LOWER median of the two, per the rule below.  They agree to 0.9% on
# receive and 0.4% on transmit, and the lowest single sample seen anywhere on
# this tree is 5,732,891 receive and 3,092,759 transmit, both far clear of the
# 12% floors (5,078,395 and 2,757,458).
#
# RAISED 2026-09-06 for 792a8cdf, the reader's dead post sweep.  BOTH numbers
# move, and the transmit one is the first time this campaign has raised it:
#
#     direction   was          now          sittings on the new tree
#     tcp-rx      5,522,706    5,594,537    5,669,851 (6 rounds), 5,594,537 (5)
#     tcp-tx      2,945,193    3,127,508    3,133,761 (6 rounds), 3,127,508 (5)
#
# The LOWER median of the two sittings is what is recorded, per the rule below,
# and the two agree to 1.3% on receive and 0.2% on transmit.  The lowest single
# sample seen on this tree is 5,464,507 receive and 3,099,971 transmit, both
# well clear of the 12% floor (4,923,193 and 2,752,207).
#
# A RECEIVE-PATH CHANGE MOVED TRANSMIT 5.3%, WHICH THE NOTE FURTHER DOWN SAYS
# CANNOT HAPPEN HERE.  That note is not wrong about the ~4.5 ms acknowledgement
# round trip; it is wrong to conclude from it that our own share of the trip is
# free.  The evidence is a null control, not an argument: origin/main built
# clean in BOTH worktrees, md5 7522050095ef on each, six rounds alternating,
# gives rx +0.22% and tx -0.00% -- 2,966,517 against 2,966,516.  The null's
# transmit stays inside 2.94-3.01M in both directories while the changed arm
# sits at 3.10-3.15M, six samples against twelve, no overlap.
#
# So read "a transmit change cannot be validated here" as "a change that only
# moves transmit THROUGHPUT cannot".  A change that shortens the CPU path
# between an arriving ACK and the window reopening does show, and shows MORE
# than on receive: during a bulk send the reader's drains are one or two frames
# a wake, so per-wake fixed cost is a larger fraction of each wake.
#
# RAISED 2026-09-06 to 5,522,706 on receive, for the two wins in d8d4eb0b.
# That is the LOWEST of main's clean-build observations, not the best:
#
#     e314b332 head arm    5,569,952
#     d8d4eb0b after arm   5,522,706   <- taken
#
# Both from CLEAN builds with the library md5 printed before a round ran, six
# rounds each alternating position.  Transmit is left at 2,945,193: the two
# changes measured +0.0% and -0.1% on it alone and -0.7% together, all inside
# what a rig whose ack is ~4.5 ms can say.
#
# RAISED 2026-09-06 for the receive campaign.  The numbers below are the
# LOWEST five-round MEDIAN observed for origin/main across five independent
# sittings, not the median of one sitting, so the baseline is never flattered
# by the run that recorded it:
#
#     sitting   tcp-rx     tcp-tx
#     q5        5,401,214  2,959,056
#     q7        5,410,138  2,945,193   <- lowest tx
#     q12       5,421,701  2,962,079
#     q13       5,423,275  2,960,043
#     q14       5,398,483  2,955,117   <- lowest rx
#
# Those medians span 0.46% on receive and 0.57% on transmit across the five
# sittings.  THAT NUMBER IS NOT THE CROSS-SITTING SPREAD AND MUST NOT BE READ
# AS ONE -- it is what five sittings happened to give on one afternoon.
#
# THAT 6.3% "DRIFT" WAS A STALE BUILD, NOT THE RIG.  It is left here because
# the correction is the useful part.  Two worktrees at the SAME commit, with
# identical source (diff -rq empty), identical submodules and identical CMake
# options, measured 5.3% apart on receive -- and their binaries differed:
#
#     clean build, either worktree   8ad54ade...  348,652 bytes
#     incremental build, worktree A  f128afbd...  351,076 bytes   <- stale
#     incremental build, worktree B  8ad54ade...  348,652 bytes
#
# A clean build of that commit is reproducible to the byte in both trees.  An
# INCREMENTAL build after `git checkout` is not: worktree A's build directory
# never matched its own commit, and with -flto one stale object relinks the
# whole library.  Every arm run out of that directory measured a binary that
# was not the commit it was labelled with.
#
# SO: BUILD EACH MEASUREMENT ARM CLEAN.  `cmake --build` on a reused build
# directory after a checkout is not a measurement, and `git checkout && cmake
# --build` between arms is how this tree produced two order-balanced,
# same-sitting results that contradicted each other -- +2.8% and -4.0% for one
# #define, decided by which directory happened to hold which arm.  Verify with
# md5sum against a clean build before believing any A/B.
#
# SO DO NOT TIGHTEN THE TOLERANCE.  12% looks generous next to 0.46% and is
# not: it is absorbing rig drift, and a tighter one manufactures red runs on
# an unchanged tree.  The 4.3% regression that reached 0.26.3 was not let
# through by the threshold, it was let through because NO WORKFLOW EVER RAN
# THIS GATE (tools/check-stage-coverage.sh exists for that now).  Wiring a
# gate up is what catches a regression; narrowing a threshold that is holding
# back real drift only breaks the gate.
#
# It also means an ABSOLUTE number from one sitting proves nothing about a
# change.  Rebuild the comparison point in the SAME sitting and alternate
# which arm runs first (see the position note above).  Every figure in this
# tree that survived did that; the ones that did not were wrong.
#
# A DELAYED LINK IS A FAR MORE PRECISE INSTRUMENT THAN THIS ONE, AND NOTHING
# HERE HAD EVER USED ONE.  run-lossgate.sh -d 50 -l 0, nine arms, same tree:
#
#     metric      median    iqr     range
#     read_kbs     538.0    0.6%     1.5%
#     write_kbs    223.0    2.7%     4.0%
#
# Against 24.3% interquartile for read on the 0 ms link and 41.7% for
# dropped_rx.  Delay paces the arrivals and the per-arm scatter collapses.
#
# BUT IT IS PRECISE ABOUT A DIFFERENT BOTTLENECK, SO DO NOT REACH FOR IT TO
# SETTLE A CPU QUESTION.  Read is 538 KB/s at 50 ms against about 690 at 0 ms.
# Delay costs no CPU, so if the processor bound both they would agree; it is
# lower, which means something other than the processor binds at 50 ms.  A two
# per cent saving in the copy path would move the 0 ms figure and leave 538
# exactly where it is, and the 0.6% spread would report that as a confident
# nothing.
#
# What it IS for: anything whose effect is on the wire rather than in the CPU
# -- window sizing, acknowledgement cadence, retransmit behaviour, loss
# recovery.  Those live in the regime it resolves.  Rates there are not this
# rig's rates either (write falls to 223 from 2,138), so a delayed run compares
# arms with each other and never against a figure taken at 0 ms.
#
# ALTERNATE THE ORDER OF AN A/B ON THIS RIG.  The 2.0% below is NOT a
# reproducible property and must not be quoted as one: a later run with clean
# builds put the SECOND position AHEAD in both arms (+0.5% and +1.8%), the
# opposite sign, and the figure below rests on three samples a cell.  Keep
# alternating anyway -- it costs nothing and it is the only thing that makes a
# position bias visible if one is there.  What follows is one sitting, not a
# law:  Six rounds against 242be840 alternating which
# tree ran first, medians, bits per second:
#
#     tcp-rx        first        second
#     242be840      5,528,920    5,434,554
#     aa0081fa      5,528,520    5,363,662
#
# The two first-position medians differ by 0.007% and both second-position
# medians sit about 2% below them, so the effect belongs to the position and
# not to either tree.  Transmit does not show it (+0.3% for second).
#
# It is worth 2% of receive, so a fixed-order pair reads a real regression as
# larger than it is and can manufacture one out of nothing: the same fix
# measured -2.7% receive against base in fixed order and +0.9% -- at base --
# when the order was alternated.  Anything in the refuted list whose receive
# verdict was within about 2% and was measured second deserves re-reading
# before it is treated as settled.
#
# It was previously rx 4764901 / tx 2651556, taken at v0.26.2 before the
# receive work landed.  Against a 25% tolerance that floor was 3,573,675, so
# a regression that gave back the whole campaign would still have passed --
# and did: the priority-inheritance commit reverted in 8e63732e cost 18% of
# transmit and this gate would not have noticed.  tools/ci.sh's rate stage now
# runs five rounds at a 12% tolerance for that reason.  The script's own
# default stays 3 rounds at 25% so a sweep can still report an arm that is
# deliberately slower.
#
# WHY TRANSMIT IS ABOUT HALF OF RECEIVE, AND WHY THAT IS NOT OURS TO FIX HERE.
# Measured 2026-09-05 with -DAMINETXDUO_RXPROBE=ON, reading netstat -s's step
# budget from a snapshot taken after the transmit arms and before any server
# arm, so the counters are transmit-only:
#
#     board     tcp-tx      ack (write to reply)   post (BeginIO to return)
#     a2065     2,036,429   4,503 us               791 us
#     ariadne   2,064,297   4,547 us               798 us
#     xsurf     1,756,793   5,070 us             1,774 us
#
# ack is the round trip and it is ~4.5 ms on EVERY emulated card, so it is a
# property of this rig -- Amiberry, the bridge, the peer -- and not of any
# driver or of anything in src/.  A real 10 Mbit card is well under 1 ms.
# Our own driver-side cost is stuff+post+reap, about 1.1 ms a frame, which
# would allow roughly 10 Mbit/s: four times what this rig delivers.
#
# So a transmit change cannot be validated here: the number it has to move is
# dominated by a term the rig sets.  Ruled out by measurement, do not retry on
# this rig: the TX ring never fills (full=0 spins=0 drops=0 over 1024 sends),
# the net68k checksum serves both directions, and NX_TCP_MAXIMUM_TX_QUEUE at 8
# against the vendor's 20 measures 2,664,243 against 2,667,163 over five
# rounds each in one sitting.
#
# CONFIRMED IN A SITTING OF ITS OWN, which is the check a raise needs and the
# previous ones did not get: a baseline set above what the tree reproduces is a
# gate that reds on an unchanged main.  Clean build of af07fc38, md5
# deef24a478bb, five rounds at the 12% CI tolerance:
#
#     tcp-rx  median 5,547,183  against 5,522,706   pct 100
#     tcp-tx  median 2,978,909  against 2,945,193   pct 101
#
# rate=PASS.  Receive clears by 0.4%, which is thin -- if a later sitting reds
# on an unchanged tree, this raise is the first thing to suspect, not the code.
#
# The application workload agrees with the direction and disagrees with the
# size, which is worth knowing before anyone quotes one number for both.
# run-fitzbench.sh, fc5fabe6 against main, six sittings an arm alternated:
# read 3,272 -> 3,562 and write 2,542 -> 2,538.  That is +8.9% on the medians
# against iperf's +3.3%, and it is a range rather than a point: the before
# arm's samples span 2,656..3,435 and the low one drags its median.
#
# A SECOND SET SETTLED IT, and settled it higher than the caveat suggested:
# before 3,296 (3,102..3,595), after 3,592 (3,387..3,746), +9.0% against the
# first set's +8.9%.  No outlier in that control arm, and its lowest AFTER
# sample beats its own before-median.  So Fitz read is +9% and the "nearer
# +7%" hedge was needed for one set, not for the result.
#
# Note Fitz gains about three times what iperf does (+9% against ~+3%).  Do not
# quote one figure for both workloads.
#
# AND DO NOT COMPARE THE TWO ABSOLUTE RATES AT ALL.  fitz_*_kbs is not a wire
# throughput.  One run's own lines: 524,288 bytes written in 142,149 eclock
# ticks, 0.200 s, 2,555 KiB/s -- against iperf tcp-tx on the same stack at
# 2,976,433 bits/s, which is 363 KiB/s.  Seven times apart, and receive is five
# times apart the same way.
#
# The iperf figure is the one that reconciles: 690 KiB/s of receive against
# 199 ns/B for the fused copy is 13.7% of the CPU for one pass and about 27%
# for two, which is exactly the per-byte share the wire profile measures.  Fitz
# at 3,562 KiB/s would want 70% for a single pass, which is not available.  The
# likely reading is that the timed section closes before the handler's buffered
# data has reached the wire, so the rate counts bytes handed over rather than
# bytes delivered.
#
# WHAT THAT DOES AND DOES NOT COST US.  The +9% is a comparison of two arms
# measured the identical way, so it stands as what an application sees when it
# reads a file over Fitz.  What it is not is evidence about the wire, and the
# absolute KiB/s must never be quoted beside an iperf rate as though they
# measured the same thing.
#
# IT IS THE STACK'S +9% THOUGH, and an earlier draft of this note wrongly left
# that open.  Both arms run the SAME fitz handler and the same everything else;
# the only difference between them is bsdsocket.library and anxnet.device.  So
# the gain is the stack's by construction, however the harness counts its
# bytes.
#
# THE OPEN QUESTION IS WHY IT IS THREE TIMES THE BULK FIGURE.  Fitz reads in
# 32 KB chunks over a request-and-response protocol; iperf is one steady
# stream.  A deeper reader drain and a read queue that finds its type first
# should both be worth more to a bursty arrival pattern than to a continuous
# one, which would explain it -- but that is a hypothesis and nothing here has
# tested it.  If it holds, the request-and-response shape is where the next
# receive work is, and this rig can see effects there that bulk iperf cannot.
#
# AND THE IPERF FIGURE ITSELF IS A RANGE.  fc5fabe6 against main was measured
# twice, each six rounds an arm with both arms rebuilt clean and md5-checked:
# +3.3% and +2.6% on receive, ahead in both positions both times.  Quote ABOUT
# +3%.  Transmit read -0.7% and then +0.3%, which is what no change looks like
# here -- the first of those two is in no sense a regression.
